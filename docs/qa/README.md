# QAテスト管理

Computer Useによる手動ブラックボックステストの仕様、実行結果、不具合・UX改善候補をGitで管理する。

## ファイル構成

| ファイル | 役割 | Git上の扱い |
|---|---|---|
| `computer-use-black-box-test-plan.md` | テスト方針、手順、期待結果、探索チャーター | レビュー対象の仕様書 |
| `test-cases.csv` | ケースID、分類、優先度などの一覧 | 差分確認しやすいケース台帳 |
| `execution-results.csv` | 環境別の実行結果 | 追記型の実行ログ |
| `issues.csv` | 不具合・UX改善候補 | 追記型の課題ログ |
| `runs/RUN-<nnn>.md` | 実行環境、集計、判断、未実施範囲 | 実行レポート |
| `evidence/RUN-<nnn>/` | Computer Useで取得した画面証拠 | 実行レポートに紐づく証拠 |
| `Shogi_Computer_Use_Test_Tracker.xlsx` | 入力規則・集計付きの操作用台帳 | 便利なスナップショット（バイナリ） |

CSVをレビューと履歴確認の正本とし、Excelはテスト実施時の入力・集計用に使う。Excelを更新した場合は、同じ変更内容を対応するCSVにも反映する。

## 運用ルール

1. UIや主要フローを変更するPRでは、影響するテストケースも同じPRで更新する。
2. テスト実行ごとに一意な`run_id`を採番し、過去の結果を上書きせず行を追加する。
3. `status`は`Not Run`、`Pass`、`Fail`、`Blocked`、`N/A`のいずれかにする。
4. `Fail`には`issue_id`、`Blocked`には`issue_id`または`blocker_fail_reason`を必須とする。
5. UX改善候補は解決案より先に、観察事実、期待、再現手順、証拠を記録する。
6. P0/P1の課題には、再現可能な手順とスクリーンショットまたはURLを残す。

## リリース前の完了条件

- 対象環境の全ケースに判定がある。
- P0の未解決課題が0件である。
- P1の未解決課題についてリリース可否の判断が記録されている。
- FailとBlockedに再現・阻害情報がある。
- 改善候補を「今すぐ直す」「後で検討」「現状維持」に分類している。

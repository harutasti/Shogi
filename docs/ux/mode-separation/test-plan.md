# 対局／解析 情報分離 UX検証計画

- 対象Issue: <https://github.com/harutasti/Shogi/issues/9>
- 対象公開版: <https://harutasti.github.io/Shogi/>
- フェーズ: Discovery / 未検証
- 作成日: 2026-07-21

## 1. 検証する仮説

対局中と解析中では利用者の目的が異なる。両方の操作を同時に表示すると、特に狭い画面で探索、スクロール、判断の負荷が増える可能性がある。

ただし、画面やモードを分けることで現在位置を見失う、切り替え操作が増える、KIF操作の所属が分かりにくくなる可能性もある。したがって「対局／解析のモード分離」は解決策ではなく比較対象の一つとして扱う。

## 2. 検証の目的

1. 現行版で主要タスクを完了するために必要な操作とスクロールを測る。
2. 初見利用者が対局開始、棋譜確認、AI解析を発見し理解できるか確認する。
3. 複数案を同じ条件で比較し、改善効果と新しい負担を明らかにする。
4. 本番実装へ進むか、現状維持または別案にするかを根拠付きで決める。

## 3. 比較対象

| ID | 案 | 要点 |
|---|---|---|
| BASE | 現行版 | 対局、棋譜、AI解析を同じページに縦配置 |
| A | モード切替 | 盤を共有し、対局／解析で操作パネルを切り替える |
| B | 展開式解析 | 対局を基本表示とし、解析をシートまたは展開パネルで開く |
| D | 情報階層改善 | 分離せず、順序、折りたたみ、CTA、見出しだけを改善する |

プロトタイプは本番コードに組み込まず、同じタスクを一通り操作できる忠実度に留める。

## 4. 評価対象

### Computer Useベンチマーク

- Chromeデスクトップ幅
- Chrome DevTools Responsive 400 × 625
- 操作者: Codex Computer Use
- 目的: 操作経路、状態遷移、到達性、スクロール、回帰の一貫比較

### 初見ユーザーテスト

- 目標: 最低5セッション
- モバイル相当を最低2セッション含める
- Computer Use比較後の第一候補Aと現行版BASEを比較する
- BとDは比較証跡として保持し、Aが判断ゲートを満たさない場合の代替候補とする
- 将棋アプリの利用経験を記録する
- 操作方法を教えず、`scenarios.csv`の`task_prompt`だけを提示する
- 個人情報は収集せず、参加者IDは匿名の`P-01`形式にする

## 5. 共通開始条件

- 公開URLを直接開く。
- キャッシュ状態とビューポートを記録する。
- シナリオ間で必要なときは新規対局またはページ再読込で初期化する。
- AIは「初級」を使用する。
- KIF読込には既存QA仕様の正常系テストKIFを使用する。
- 時間はタスク提示または最初の操作から、成功条件を満たすまで測る。

## 6. 記録項目

| 項目 | 定義 |
|---|---|
| `elapsed_seconds` | タスク開始から成功条件までの経過秒 |
| `click_count` | クリックまたはタップの回数。盤上の着手も含む |
| `scroll_count` | 意図的なスクロール操作の回数 |
| `key_count` | ショートカットやナビゲーションキーの回数。文章入力は1操作として備考へ記録 |
| `error_count` | 目的と異なる操作、誤った対象選択、意図しない状態変化 |
| `recovery_count` | 戻る、閉じる、再試行など誤操作からの復帰回数 |
| `observation` | 画面上で確認できた事実。改善案と分けて記載 |
| `status` | `Pass`、`Fail`、`Blocked`、`Not Run` |

Computer Useの経過時間には自動操作基盤の待機時間が含まれるため、人間のタスク時間と直接比較しない。同じ方式・同じ環境内の相対比較にのみ利用する。

## 7. 初見ユーザーテストで追加する観察

- 最初に注目した場所
- 対局開始と解析開始を探した経路
- 発話、ためらい、質問
- 現在の手数、手番、解析状態を正しく説明できるか
- 盤面と操作パネルの関係を理解できるか
- 安心して操作できたかを5段階で回答

誘導質問を避ける。「分かりにくいですか」ではなく「今どのような状態ですか」「次に何をしようとしていますか」と尋ねる。

## 8. 成功指標の仮置き

ベースライン取得後に確定する。

- 主要タスク完了率を下げない。
- 対局終了から最善手確認までの中央値を25%以上短縮する。
- 400px幅で解析到達までのスクロール回数を50%以上減らす。
- 対局開始の時間と操作回数を悪化させない。
- 状態消失、意図しない棋譜破棄、誤った新規対局を発生させない。
- キーボードとスクリーンリーダーで現在の表示区分を識別できる。

## 9. Apple Design観点の評価

- **Purpose**: 現在の目的に必要な操作が先に見えるか。
- **Agency**: 利用者が状態を失わず、いつでも別の作業へ移れるか。
- **Familiarity**: 切り替え、シート、折りたたみが見た目どおりに動くか。
- **Flexibility**: デスクトップと狭い画面で同じ情報を無理に押し込んでいないか。
- **Simplicity**: 要素を隠しただけではなく、主要経路の理解が容易になったか。
- **Craft**: 押下フィードバック、焦点、Reduced Motion、空間的一貫性が保たれるか。

## 10. 判断ゲート

本番実装へ進むには、次をすべて満たす必要がある。

1. 現行版と3案を同じシナリオで比較済みである。
2. Computer Use結果と初見ユーザー結果を分けて記録している。
3. 主要指標が改善し、重大な迷いまたは状態喪失が増えていない。
4. デスクトップと400px幅の両方で成立する。
5. 実装・保守コストが改善効果に見合う。
6. `decision.md`に採用、不採用、保留のいずれかと根拠を記録する。

検証が不十分な場合は実装へ進まず、追加検証または現状維持とする。
